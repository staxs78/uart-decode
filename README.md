# uart-decode — decode UART bytes from scope / logic-analyzer captures

[![tests](https://github.com/staxs78/uart-decode/actions/workflows/tests.yml/badge.svg)](https://github.com/staxs78/uart-decode/actions/workflows/tests.yml)
![python](https://img.shields.io/badge/python-3.10%2B-blue)
![deps](https://img.shields.io/badge/dependencies-none-lightgrey)

A small, dependency-free tool that turns a raw waveform capture from a **silent
serial console** into decoded bytes: estimated baud, LSB-first framing,
extracted bytes/ASCII, framing-error and idle-level statistics.

It needs **no uniform sample rate**. It works from the edge list you already
have (oscilloscope CSV, a logic analyzer export, VCD, or plain two-column
`time,value` text), so a capture with a variable or slow sample clock is fine.

```
python uart_decode.py capture.csv
python uart_decode.py capture.vcd --vcd-signal clk
python uart_decode.py capture.csv --parity even --data-bits 8
```

Exit code `0` = ran (even with zero frames found), `2` = bad/unusable input.

## Why this exists

A very common hardware situation: a board (router, ONT, embedded gear) has a
UART console pad, the wiring and probe look correct, but the USB-serial adapter
returns **zero bytes**. Two separate questions get conflated:

1. *Is there actually a console signal on that line?* (or is the pad gated,
   on the wrong side of a series link, or an RX line that idles high forever)
2. *If there is, what did it say?*

A scope capture answers (1) and can answer (2) — but only if something decodes
it. This tool does that. It is deliberately paranoid about the things that make
real captures hard:

- **Unknown baud.** It recovers the bit time from the data instead of asking.
- **Unknown idle level / inverted captures.** It tries several idle
  hypotheses, including captures where the probe inverts the signal.
- **Gated bursts.** Boot banner, then 1.5 s of silence, then more output — the
  decoder walks across long gaps.
- **Jitter and noise.** ±2–3% bit jitter and voltage noise still decode.

## How it works

1. Threshold the signal at mid-level → edge list.
2. Try idle-level hypotheses (first level, last level, longest-held level,
   longest single run); pick the one that admits the most valid frames. This is
  what makes inverted / low-idle captures work.
- Estimate the bit time as the **largest period that explains every active run
  and every frame-to-frame spacing as an integer number of bits**, then retry
  `/2 /3 /4` divisors; keep the hypothesis with the highest share of valid
  frames (ties go to the larger period, so subdivisions can't win on frame
  count alone).
- Sample each frame at bit centres: start, 8 data bits (LSB first), optional
  parity, stop.

## Assumptions & limitations

- 5–8 data bits, none/even/odd parity, 1 stop bit. It is not a decoder for
  arbitrary line protocols (SPI/I2C/CAN) — UART framing only.
- It estimates the bit time; it does not know the nominal baud. Read the
  reported estimate (and its range) as evidence, not a datasheet value.
- A capture with no edges at all is reported as such (exit 2 for flat input);
  "no signal" is a valid, useful answer.
